# Анализ статистики трасс браузерного моста

Документ описывает, как по логам проверить, что агент получил тот же ответ,
который провайдер в итоге показал на странице, и как найти черновики, утёкшие в агент.
Часть, общая для всех провайдеров, описана здесь; особенности конкретного
провайдера — в отдельных дополнениях (`docs/<PROVIDER>_TRACE_STATS.ru.md`).

Сверку отдачи с ответом на странице выполняет только провайдер, вкладка
которого присылает метаданные `settle` (список `_SETTLE_EXTRA` в
`providers/tab_bridge.py`). Доля корректных ответов модели (`outcomes`)
считается для всех провайдеров.

## Как получить данные

1. В `.env` включено `TOOLCALL_LOG=1`. Каждый чат агента пишет файл
   `logs/<MMDDhhmmss>-<provider>.log`.
2. В Tampermonkey стоят текущие версии скриптов из
   `session/browser-bridge/userscripts` (их пишет `python -m providers.tab_bridge`),
   вкладка перезагружена.
3. Перед новой серией прогонов старые логи переносятся из `logs/`, иначе их
   цифры смешаются с новыми (поля и критерии менялись между версиями).
4. Сводка:

   ```powershell
   python -m server.trace_report logs
   ```

   Отчёт содержит только счётчики: ни промптов, ни ответов, ни аргументов инструментов.

## Поля сводки: исходы шагов (все провайдеры)

| Поле | Значение |
|---|---|
| `outcomes.calls` / `outcomes.text` | шаги, отданные агенту как вызов инструментов / как текст |
| `outcomes.model_format`, `model_schema`, `model_incomplete` | ответ модели нарушил контракт (`invalid_tool_response`) |
| `outcomes.bridge_state` | сбой моста или вкладки |
| `outcomes.request_refused`, `unknown` | отказ запроса / нераспознанный ответ |
| `model_steps`, `model_step_success` | число шагов модели и доля успешных (`calls + text`) |
| `by_day` | то же по дням (`MMDD` из имени лога) |

## Раздел `bridge settle` в логе хода

Если вкладка провайдера присылает метаданные, в логе хода после `from provider` есть:

```
------------ bridge settle---------------
{ ...метаданные... }
```

Сервер пропускает только поля из белого списка: числа и флаги, без текста.

**Важно:** `late_rewrite` и `dom_check` в разделе файла N описывают **ответ из
файла N−1** (предыдущего хода). Проверка идёт после отдачи ответа, и её результат
уходит на сервер вместе со следующим ходом. Следствия:

- у последнего хода сессии проверки нет, пока не отправлен следующий промпт;
- у хода, собранного из DOM (`source: "dom"`), проверки нет;
- сопоставлять надо так: `from provider` в файле N−1 ↔ `dom_check` в файле N.

### Общие поля

| Поле | Значение |
|---|---|
| `source` | `wire` — ответ взят из сетевого потока; `dom` — собран из текста страницы |
| `tool` | в отданном тексте есть ```` ```tool_calls ```` (в том числе если блок просто упоминается в тексте) |
| `quiet_ms` | время от последнего сетевого события до отдачи |
| `stable_ticks` | только для `dom`: сколько тиков текст на странице не менялся |
| `late_rewrite` | после отдачи пришёл другой закрытый ответ для того же чата (до нового задания): `delay_ms`, `tool_before`, `tool_after` |
| `dom_check` | сверка ответа предыдущего хода со страницей, см. ниже |

Поля конкретного провайдера описаны в его дополнении.

### Поля `dom_check`

| Поле | Значение |
|---|---|
| `found` | на странице найден пузырь ответа |
| `exact` | совпадают все буквы и цифры (разметка Markdown игнорируется) |
| `match` | `exact` или `similarity` ≥ 97% при разнице длины ≤ 5% (шум преобразования Markdown ↔ DOM) |
| `similarity` | пересечение множеств слов, % от суммы обоих текстов; падает и при подмене, и при лишнем тексте на странице |
| `coverage` | доля слов отданного текста, найденных на странице, %; около 100% при лишнем тексте на странице (диаграммы), низкий при подмене |
| `changes` | сколько раз пузырь менялся после отдачи |
| `stable_ms` | сколько пузырь не менялся к концу наблюдения |
| `wire_len`, `dom_len` | длины отданного текста и текста пузыря |
| `tool_wire`, `tool_dom` | есть ли ```` ```tool_calls ```` в отданном тексте и в пузыре |
| `ended` | `next_job` — наблюдение закончилось новым заданием; `timeout` — прошло 15 с (пользователь долго не писал, это нормально) |

## Поля сводки: блок `bridge_settle`

Блок разбит по провайдерам (суффикс имени лога). Каждое значение — число ходов,
где условие выполнено, кроме выборок `…_ms`/`dom_similarity`/`dom_coverage`
(`count`, `min`, `max`, `avg`).

| Поле | Значение |
|---|---|
| `turns` | ходов с разделом `bridge settle` |
| `source_dom` | ходов, завершённых по тексту страницы |
| `tool_envelope` | ходов, где в отданном тексте есть ```` ```tool_calls ```` |
| `late_rewrite`, `late_rewrite_delay_ms` | ходов с поздней перезаписью и её задержки |
| `dom_check` | ходов со сверкой |
| `dom_mismatch` | сверка не совпала (`match: false`), всего |
| `dom_render_extra` | из них: на странице есть весь отданный текст и ещё что-то (`coverage` ≥ 97, `dom_len > wire_len`) — отрисовка, не подмена |
| `dom_suspect` | из них: всё остальное — **кандидаты в настоящий пропуск** |
| `dom_tool_mismatch` | из них: ```` ```tool_calls ```` есть только с одной стороны |
| `dom_changed_after_emit` | пузырь менялся после отдачи |
| `dom_similarity`, `dom_coverage` | выборки `similarity` и `coverage` |

## Критерии

### Норма

- `dom_suspect = 0` и `dom_tool_mismatch = 0`;
- `model_step_success` близко к 1, `bridge_state` редок;
- `late_rewrite = 0`;
- `source_dom` не больше числа ходов, где провайдер по своим правилам может
  завершаться по странице (см. дополнение провайдера).

`dom_render_extra > 0` допустимо: так выглядят ответы с диаграммами (`mermaid`)
и другими виджетами, где страница добавляет подписи и кнопки.

### Критично (агент мог действовать не по итоговому ответу)

| Признак | Что значит | Что делать |
|---|---|---|
| `dom_tool_mismatch > 0`, `tool_wire: true`, `tool_dom: false` | агент выполнил вызов инструмента, которого на странице в итоге нет (черновой вызов) | найти ход, сохранить лог как доказательство, разобрать по шагам ниже |
| `dom_tool_mismatch > 0`, `tool_wire: false`, `tool_dom: true` | страница в итоге показала вызов инструмента, а агент получил текст | то же |
| `dom_suspect > 0` с `coverage < 90` | агент получил заметно другой текст | сравнить `from provider` в файле N−1 с тем, что видно на странице |
| `dom_check.changes > 0` | страница перерисовала ответ уже после отдачи агенту: мост отдал раньше, чем сайт закончил | смотреть `quiet_ms` и `stable_ms`; если повторяется, окно ожидания мало |
| `late_rewrite > 0` | после отдачи пришёл ещё один закрытый ответ с другим текстом | то же; задержка из `late_rewrite_delay_ms` подскажет нужное окно |

### Предупреждения

- `source_dom` растёт там, где должен работать сетевой захват;
- `dom_check.found: false` — изменилась разметка страницы, сверка не видит пузырь;
- ошибки `bridge_state` — мост не дождался готового ответа; подробности в
  подсказке значка вкладки и в консоли страницы.

## Разбор подозрительного хода

1. Найти файлы, где в `dom_check` стоит `match: false` (поиск по `"match": false` в `logs/`).
2. Для файла N открыть файл N−1 и его раздел `from provider` — это то, что получил агент.
3. В разделе `bridge settle` файла N−1 посмотреть поля провайдера (см. его дополнение):
   были ли разные версии ответа и какую мост выбрал.
4. В `dom_check` файла N посмотреть `coverage`, `wire_len`/`dom_len`,
   `tool_wire`/`tool_dom`, `changes`. Высокий `coverage` и `dom_len` заметно больше
   `wire_len` — отрисовка. Низкий `coverage` — подмена.
5. Косвенная проверка: следующий промпт модели (раздел `to provider` файла N)
   продолжает именно тот ответ, который получил агент, или тот, что видно на странице.

## Как подключить сверку для другого провайдера

Серверная часть, отчёт и механизм в userscripts общие; провайдер добавляет только своё.

Что уже есть в userscripts:

- наблюдатель: `emitBody(job, status, bytes, path, requestTurn, settle, answerText)`
  кладёт в событие ответа `settle` (уходит на сервер) и `answer_text` (остаётся на
  странице, только для сверки);
- контроллер: пересылает `settle` в `/browser/result`; принимает событие
  `{late_rewrite: {...}}` и отправляет его со следующим ходом; если у сайта есть
  `answerSnapshot` и в событии пришёл `answer_text`, запускает `domCheck` и
  отправляет `dom_check` со следующим ходом; новое задание останавливает наблюдение.

Алгоритм `domCheck`: опрос последнего пузыря каждые 250 мс до нового задания
(не дольше 15 с), затем сравнение:

- слова — последовательности букв и цифр (`/[\p{L}\p{N}]+/gu`) в нижнем регистре;
- `exact` — склеенные слова совпадают;
- `similarity = round(200 · общие / (слов_отдано + слов_на_странице))`,
  общие — пересечение мультимножеств слов;
- `coverage = round(100 · общие / слов_отдано)`;
- `match = exact || (similarity ≥ 97 && |wire_len − dom_len| ≤ 5% от большей длины)`;
- остальные поля — по таблице `dom_check` выше; никакого текста в результате.

Шаги подключения:

1. **Контроллер.** В описание сайта добавить
   `answerSnapshot: () => [тексты пузырей ответа, от старых к новым]`.
2. **Наблюдатель.** Передать отданный текст ответа в `emitBody` (`answerText`)
   и, по желанию, `settle` с общими полями и полями провайдера; событие
   `late_rewrite`, если провайдер умеет переписывать ответ после отдачи.
3. **Сервер.** Добавить провайдера в `_SETTLE_EXTRA` в `providers/tab_bridge.py`:
   `None`, если своих полей нет, иначе функцию, копирующую его поля через белый список.
4. **Отчёт.** Свои счётчики — функция в `_SETTLE_EXTRA` в `server/trace_report.py`;
   общие счётчики появятся сами.
5. **Документ.** Дополнение `docs/<PROVIDER>_TRACE_STATS.ru.md`: как устроен ход
   провайдера, его поля и критерии.

## Диагностика страницы

Консоль вкладки:

- `[opencode] rendered answer differs from emitted wire` — расхождение со страницей
  (с метаданными `dom_check`);
- `[opencode] late rewrite after emit` — поздняя перезапись.

## Что передать в другой чат для анализа

- вывод `python -m server.trace_report logs`;
- для подозрительных ходов — разделы `bridge settle` файлов N−1 и N
  (в них нет текста ответов) и, если не жалко, `from provider` файла N−1;
- версии скриптов (`@version` в заголовках userscripts);
- этот документ и дополнение провайдера.
